# Runtime details implementing the written specification

The following named mechanisms implement existing requirements; they do not change the action matrix, calibration, freshness gate or taxonomy.

- **Measured structural deadline:** the deadline is `known_to_us_at + 3 minutes`. Classification and generation after that instant are explicitly marked late. First successful delivery stores its actual timestamp, latency and deadline result. Recovery does not pretend a late first card met the target; the existing analyst receives the deadline and remains responsible for calling publish_card; no separate code publisher or extra job type is introduced.
- **Completed confirmation windows:** multi-window market persistence uses non-overlapping completed window endpoints. Event invalidation predicates are reevaluated on every tick and are not throttled by hourly market confirmation counters.
- **Automated scout hooks:** the scheduler emits evidence-backed proposals for the written UNKNOWN-market-state, source-opportunity and alternative-explanation criteria. Repeated scans of identical evidence do not create extra occurrences or review jobs. The event tool separately captures a proposed beneficiary layer outside the canonical eight. All reviews use the lowest queue priority, and proposals default to SUBCATEGORY. These hooks never promote a category or modify production rules.
- **Reaction late-data revisions:** `tank reaction EVENT --token-id TOKEN --recapture CHECKPOINT --reason TEXT` queues the next immutable checkpoint revision. A reason and existing checkpoint are required. Revisions preserve the original anchor/window, reference the previous revision, and retain all earlier values. The same revision is idempotent; ordinary scheduler scans continue to target revision one and cannot cause a revision storm.
- **Call expiry is a tracking notice:** at seven days the scheduler atomically records pending expired-call IDs, closes the call as EXPIRED and queues the session message. The resulting card explicitly says tracking ended; its frozen prior decision is non-actionable and cannot reopen a START on delivery. Pending expiry markers are consumed only by a SENT card containing those exact call IDs, so delivery failures or newer expiries cannot silently erase the required notice.
- **Durable ordinary update rate window:** a material ordinary update is frozen as an immutable candidate even when the fifteen-minute delivery window is still closed. Its DELIVER job is scheduled from the last actual SENT timestamp, not the newest generated candidate. Delivery rechecks the window under the event lock and reschedules without consuming a retry attempt. Newer pending versions coalesce older UPDATE candidates; an already delivered newer version also suppresses older cards. Suppression is an append-only GENERATED ledger entry with a reason, never a forged SENT. START, EXIT and unresolved-FATAL updates retain their existing immediate rule; tracking-expiry notices can escape stale-origin rejection but retain the ordinary fifteen-minute window. The event lock spans the policy check, Telegram send and SENT transition so an obsolete pending card cannot follow a newer delivered EXIT.
